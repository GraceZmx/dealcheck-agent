## 3. 关键产品决策和理由

### 架构与模型
| 决策 | 理由 |
|---|---|
| **混合架构**：规则负责报价、条款、硬性规则、打分和决策；Agent 只负责调查并带来源汇报 | 涉及钱和底线的判断必须可复现、可解释；开放信息（口碑、价值观、同行报价）只有 Agent 能查。Agent 的结论里没有"决策"字段（G6） |
| 先做**海外英文市场**（IG / TikTok / YouTube），界面英文，代码注释和文档中文 | 先跑通一个市场；V3 再本地化到小红书、抖音 |
| 模型从 Claude 改为 **DeepSeek**，Claude 保留为可替换的备选；不用厂商 SDK，自己实现 Agent Loop | 用户决定。自己封装可以保证换模型时行为一致 |
| **思考模式默认关闭** | 小实验里质量没有可见差别，关闭后更快、更便宜，也不会出现"思考把额度用完、没有输出"的空回复；M4 再在评测集上对比 |
| 结论通过 **`submit_findings` 工具**提交，而不是直接输出 JSON 文本 | 开启思考时模型会把 JSON 包在代码块里；工具参数天然是 JSON，再用 Pydantic 校验 |
| MVP 用**结构化表单**输入；粘贴合同原文由 LLM 抽取放在 P1；PDF 上传不做 | 规则需要结构化字段，表单最可靠 |

### 数据与规则
| 决策 | 理由 |
|---|---|
| 基准表 = **基础价（平台 × 量级 × 形式）× 领域系数**，主来源 IMH 2026 | 公开报告大多不细分到领域，硬凑 240 个价格就等于编数据 |
| **绝不编数据**：查不到的标低置信度，领域系数取 1.0（Gaming 就是这样处理的） | 见 `backend/data/BENCHMARK_SOURCES.md` |
| **领域系数取来源区间的下限** | 避免和全市场混合价重复计算；基准偏高会误导博主还价、谈崩合作，代价更大 |
| 互动率修正 V0 不启用（配置里保留开关，打开会直接报错） | 没有找到可靠的分平台、分量级互动率基准 |
| 硬性规则分两级：**拒绝类**（HR-1/2/3）和**封顶类**（HR-4~8）；Agent 推翻不了 | 用户底线零容忍；证据不足时只封顶、不直接拒绝 |
| 拒接品类两级：**标准清单 13 项精确匹配 → HR-1 拒绝**；**自由填写由 Agent 语义判断 → HR-8 只封顶 + 提示用户核实** | 语义判断可靠性低。HR-8 只认档案里确实写了的条目，防止 Agent 自己编拒接理由 |
| 严重负面需要 **≥ 2 个独立来源**（按域名计算）才拒绝，只有 1 个来源时封顶 | 避免误伤品牌，降低诽谤风险 |
| Agent 调分要附有效来源，否则作废；单项有范围，合计不超过 ±15 | 限制 Agent 对决策的影响幅度 |
| values fit 只评估价值观匹配，**拒接品类不重复扣分** | 本地实测发现的问题：一个酒精饮料品牌曾因拒接品类被 values fit 重复扣分 |

### 护栏与安全
| 决策 | 理由 |
|---|---|
| `fetch_page` **只接受编号**；来源列表由程序根据编号生成（G3） | Agent 编造不出 URL，也读不了任意网址 |
| **G12 引用一致性**：正文里出现的每个编号都必须在来源列表里；不存在的编号删除并标记 "unverified" | Badcase BC-1（PRD 8.5 节） |
| 每次评估最多 3 次搜索、3 次读网页、8 次模型调用、120 秒、¥0.50，由程序强制执行 | 控制成本和耗时 |
| 邮件里的数字只来自规则（占位符），模型写的数字会被拒绝并改用模板；**不提供发送功能** | 防止编造金额；发出去的邮件收不回 |
| 创作者**姓名只存在浏览器里**，由前端在本地替换署名，完全不发送到服务器；发给模型的档案也不含最低接单价和原始粉丝数 | 隐私；DeepSeek 的数据可能存储在境外 |
| 预检已命中拒绝类规则时**跳过 Agent** | 结论已经确定，没必要花钱调查 |

### 界面
| 决策 | 理由 |
|---|---|
| **SSE 实时显示 Agent 真实步骤**，不用和真实步骤无关的轮播提示；SSE 失败时回退为普通请求 | 符合"透明可追溯"的产品原则 |
| **调查进行中不显示结论**，只显示 "Checking the brand…" 和规则已经确定的部分 | 用户提前离开也不会拿到错误结论 |
| 命中拒绝类规则时突出显示规则原因，分数弱化并标注 "overridden"；封顶类注明"按分数本应是接受" | 避免高分让用户困惑 |
| 三类信息标签：Rule-based / Sourced / Insufficient info；来源角标 [n]，链接去掉跟踪参数 | 可解释性（PRD 11.1 节） |

### 部署与防刷
| 决策 | 理由 |
|---|---|
| 网站完全公开，部署在 Render 免费版 | 方便别人体验；正式演示前再考虑升级到 Starter（$7/月，不休眠） |
| 每个 IP 每天 5 次 AI 评估、全站每天 ¥5、每个 IP 每分钟 30 次请求、总开关 `AGENT_ENABLED` | 防止有人刷光余额；超出后降级为仅规则模式，不报错 |
| 计数存在内存里，**DeepSeek 账户只保留少量余额**作为最后一道保险 | 简单；重启或休眠会清零，所以靠余额兜底 |
| 真实 IP：**优先 `True-Client-IP`**，回退到 `X-Forwarded-For` 右数第 3 个 | 线上实测：`X-Forwarded-For` 最右边是 Render 内部地址（如果取它，所有访客会被当成同一个 IP）；`True-Client-IP` 由 Cloudflare 覆盖写入，伪造不了 |

### 评测（M4）
| 决策 | 理由 |
|---|---|
| **不做创作者访谈和 Reddit 招募**，移到 PRD 第 17 节"未来计划"；**标准答案只由用户一人标注** | 用户决定（2026-10-26） |
| 一人标注的防偏差流程：书面标注准则 → 跑系统前标完并加密备份到 iCloud → **`deepseek-v4-pro` 盲标作参考** → 跑系统后改标签必须记录原因 | 没有第二个人审核。盲标模型和被测模型同一家公司，可能有相同偏差（已写进 PRD 第 15 节风险） |
| **不做自我重标**（原计划 2–3 天后自己盲标第二遍） | 用户决定（2026-10-26）：求职作品，时间有限。作为已知局限写进 PRD 14.1 和第 15 节；改进方向是真上线时请 2–3 位创作者独立标注 |
| **20 个真实品牌 + 5 个虚构品牌**；之前本地测过的 5 个品牌不进评测集 | 虚构品牌查不到信息会触发 HR-7、到不了"接受"，只用在不受影响的地方；测过的品牌已经看过系统结论，标注会受影响 |
| **15 个校准组 + 10 个测试组**，校准只用校准组 | 用自己标的答案调阈值再打分，偏差会被放大两次。测试组只有 10 个，结果是方向性的 |
| **分数区间不人工标注**，按决策自动生成（接受 75–100 / 谈判 50–74 / 拒绝 0–49）；命中任何硬性规则的案例不检查分数 | 精确标分数很主观；命中硬性规则时分数可能落在任何区间 |
| 标注从"给创作者朋友建议"的角度判断，**不照抄系统阈值**；报价参考用"低于区间下限 = 偏低、不到下限一半 = 离谱"，和系统的分档标准不同 | 标准答案照抄规则的话，"仅规则"配置会自动满分，消融实验失去意义 |
| 真实品牌案例和运行结果只放 `local/eval/`；案例编号 `R01`–`R20` / `F01`–`F05`，不带品牌名 | 之前有一次品牌名通过文件名进了仓库 |
| **品牌调查由 Claude 辅助完成，决策由用户判断**：不用 DealCheck 系统调查；调查卡片只列事实和来源；之前测过的 5 个品牌不用；候选品牌名全部加进 `local/brand_blocklist.txt` | 用户没时间自己查 20 个品牌。已写进 PRD 第 15 节风险 |

### 工作约定
- **任何时候都不读取、显示或打印 `.env` 的内容**，只检查变量是否存在。
- **真实品牌只在本地测试**（`local/`、`traces/` 都被 git 忽略）；仓库里的样例、测试和文档只用虚构品牌或匿名描述。
- **提交前自动检查**（`scripts/check_brands.py`，由 `.githooks/` 的 git 钩子触发）：暂存区出现 `.env` / `.venv`、`local/` / `traces/` 下的文件，或者新增内容、文件名、提交信息里出现真实品牌名，就拒绝提交。
  - 品牌名单只在本机：自动收集 `local/eval/cases/`、`local/real_deals/` 里的品牌名和官网域名主体，再加上手动补充的 `local/brand_blocklist.txt`（别名、母公司、当地合作方；本身是普通单词的品牌写成 `case:Name`）。名单为空时只提示、不拦。
  - 换电脑或重新克隆后要运行一次 `git config core.hooksPath .githooks` 启用。
  - 往名单里加了新品牌后，运行 `python scripts/check_brands.py --all` 扫描全仓库。
  - **不使用 `git commit --no-verify` 绕过检查**；被拦住时停下来，告诉用户命中了什么，由用户决定怎么改。
- 每完成一步就跑 pytest 并提交；推送时机按用户的指示。
- 用户是编程新手，说明要用大白话；需要用户操作的步骤要写清楚点哪里、填什么。

## 4. 已知问题与待办

### 已排查：来源 [9]（BC-2，误报）
- **现象**：本地网页评估一个酒精饮料品牌时，一条来源的标题是另一家公司被投诉的裁定，看不出和品牌有关，链接又被防机器人页挡住，看起来像引用错误。
- **结论（2026-10-26）**：误报。用户人工核对广告监管机构官网的同一份裁定，品牌、创作者 Instagram 广告、具体内容、"已和解"四项都对得上，那家公司是该品牌在当地的合作方。详见 PRD 8.5 节 BC-2。
- **已修复**：
  1. 新增 `SAVE_WEB_TRACES` 开关（默认关闭，只在本机 `.env` 打开），网页评估也保存运行记录到 `traces/`，文件名带 `web`；
  2. 运行记录完整保存搜索摘要和网页正文，不再截断到 300 字（发给模型的内容不变）。
- **仍待做（并入 M4）**：
  1. "来源支持度"检查：G3 / G12 只能保证编号确实是本次搜到的网页，保证不了内容支持结论。用 LLM-as-Judge 判断结论和来源摘要是否一致，并统计"来源有效率"（PRD 13.2 节目标 ≥ 90%）；
