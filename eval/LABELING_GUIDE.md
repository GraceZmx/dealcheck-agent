# DealCheck 评测集标注准则

> 用途：给评测集的每个案例标"标准答案"。标准答案只由产品负责人一人标注，所以这份准则同时规定了减少个人偏差的流程（第四节）。
> 案例文件格式见 `eval/README.md`。

---

## 一、核心角度

想象一个没有经纪人、自己谈合作的创作者朋友，把这封合作邀请转给你，问："这个能接吗？"

你只能给三种回答：

| 决策 | 你会对朋友说 | 判断方法 |
|---|---|---|
| **接受** | "可以签，基本不用改。" | 原样签下去，你一点都不担心 |
| **谈判** | "值得回，但先把 X 改了，或者先把 Y 搞清楚。" | 如果对方答应你所有合理的要求，你会让朋友接 |
| **拒绝** | "别花时间了。" | 就算对方答应合理的要求，你还是不会让朋友接；或者这件事碰了朋友的底线 |

**两个判断方法：**

1. **原样签你担心吗？**不担心，就是"接受"。
2. **对方让步之后你会接吗？**会，就是"谈判"；不会，就是"拒绝"。

---

## 二、判断顺序（每个案例按这 5 步走）

### 第 1 步：碰没碰底线？这是唯一一步直接按产品规则来标

底线是创作者自己定的，或者是产品对用户的承诺，**不靠你个人判断**：

- 品牌属于朋友在标准清单里勾选的拒接品类 → **拒绝**
- 要求朋友先付钱（买产品、交押金、交"会员费"等）→ **拒绝**
- 严重负面（诈骗、监管处罚、多起拖欠创作者款项、产品召回）有 **2 个以上不同网站**证实 → **拒绝**
- 严重负面只有 1 个网站说 → 最多到**谈判**（"先核实"）
- 品牌和朋友**自己写的**拒接品类明显相符 → 最多到**谈判**（"请朋友自己再确认"）

如果你个人不同意某条规则的处理方式（比如你觉得自由填写的拒接品类命中了，也应该直接拒绝），**照规则标**，再把你的看法写进 `rationale`。这样记下的是对产品的反馈，标签本身保持不变。

### 第 2 步：品牌查得到吗？

你自己花几分钟搜一下，确认不了这家公司是谁（官网对不上、几乎没有信息），就**不能标"接受"**。条件再好也是"先要公司信息"，标谈判。

### 第 3 步：钱给得够不够？

先查市场区间：在 `backend/data/benchmarks_v0.json` 里找到对应**平台 × 粉丝量级 × 内容形式**的那一行，`p25` 是区间下限，`p75` 是区间上限，再乘上 `niche_coefficients` 里这个领域的系数。交付多条内容时按条数相加。

然后问自己："这个价，朋友接了会不会觉得亏？"参考说法：

| 报价 | 算什么 | 一般怎么处理 |
|---|---|---|
| 在市场区间里或更高 | 钱没问题 | 不影响决策 |
| 低于区间下限 | **偏低** | 还一次价，往往能谈到合理水平 → 谈判 |
| 不到区间下限的一半 | **离谱** | 正常还价很难追上 → 往拒绝方向考虑，再结合合同和品牌一起判断 |

补充说明：

- 合同要求付费投放、永久使用权或较长的独家期时，朋友理应多收钱。这时同样的报价要往"偏低"那边看。
- 低于朋友设定的最低接单价 → 最多到**谈判**（这是朋友自己定的线）。
- **不要去算系统用的报价比和分档。**上面的参考说法故意用了和系统不同的标准，你按"朋友会不会亏"来判断就行。

### 第 4 步：合同有没有坑？

这些是常见的坑。只要能谈掉，通常就是**谈判**：

- 永久使用权，或者付费投放不另外给钱
- 没有撤单费（品牌临时取消，朋友白干）
- 独家期太长、范围太宽，又没有额外补偿
- 修改次数没有上限

**几个坑同时出现，钱又给得低**，说明对方没诚意，往拒绝方向考虑。

### 第 5 步：品牌靠不靠谱、和朋友搭不搭？

- 有零星差评（审批慢、沟通差），但没有拖欠付款 → 不影响决策，可以写进风险点。
- 品牌主张和朋友的价值观明显冲突（比如朋友主打环保，品牌却以过度包装出名）→ 至少谈判；冲突严重就拒绝。
- **品牌有名，不代表合作就好。**大品牌开低价、塞霸王条款的情况一样常见。

### 最后合起来看

- 5 步全部没问题 → **接受**
- 碰了底线，或者问题多到让步也救不回来 → **拒绝**
- 其他情况 → **谈判**

## 三、每个字段怎么填

| 字段 | 怎么填 |
|---|---|
| `decision` | 按上面的流程判断，只填一个决策 |
| `boundary` | 两个决策都说得通时，选你更倾向的那个，标 `true`，并在 `rationale` 里写清楚另一个为什么也说得通 |
| `confidence` | **高**：换个时间再标，你几乎肯定还是这个答案。**中**：大概率是，但有一处拿不准。**低**：主要靠感觉，或者关键信息不够 |
| `rationale` | 2–4 句话，写成你会对朋友说的话，不用写分数 |
| 分数区间 | **你不用填**，评测脚本会根据决策自动生成，规则见 `eval/README.md` |
| `hard_rules.must_hit` | 第 1、2 步里命中的规则，以及明显的红灯条款（HR-4）、低于最低接单价（HR-5） |
| `hard_rules.must_not_hit` | 明显不该触发的规则。比如知名品牌不该触发 HR-7；没有负面的品牌不该触发 HR-2 和 HR-6 |
| `key_risks` | 一个称职的朋友**一定会提醒的** 2–4 件事。能对应到条款红黄灯、具体规则、品类或报价位置的，写成可自动检查的类型；其他的写成 `judge` |
| `must_not_claim` | 只有当你预计 Agent 可能会编出来时才填。比如查不到信息的品牌，不该说它有负面记录 |
| `evidence`（只有真实品牌） | 你做判断时依据的事实，每条附链接和查看日期。最多 3–5 条，每个品牌调查不超过 15 分钟 |

## 四、防偏差规则（没有第二个人审核，就靠这些）

1. **先标完，再跑系统。**25 个案例全部标完、把 `local/eval/` 打包成带日期的加密压缩包放进 iCloud 之后，才第一次运行评测。`labeled_before_first_run` 一律填 `true`。
2. **调查品牌不用 DealCheck。**用浏览器自己搜，否则就是拿系统的答案来出系统的考题。
3. **之前测过的品牌一律不用。**M2、M3 阶段在本地用真实 Agent 跑过的 5 个品牌（`local/real_deals/` 里那 5 个），你已经看过系统对它们的结论，判断会受影响，**全部换成新品牌，不进评测集**。
4. **按创作者场景出题，不按"想让系统通过 / 不通过"出题。**设计案例时想的是"朋友真的会收到什么样的邀请"，而不是"系统哪条规则会被触发"。
5. **2–3 天后自己盲标第二遍。**打乱顺序，遮住第一遍的答案和理由，只看输入重新判断。两遍不一致的案例要重新想一遍，定下最终答案，并把它标成边界案例或降低置信度。结果记在 `relabel` 里。
6. **模型盲标只作参考。**`deepseek-v4-pro` 只拿到案例输入和这份准则，看不到系统输出，也看不到你的答案。凡是它和你不一致的案例，你都要重新看一遍，但**最终由你决定，不能直接采用它的答案**。结果记在 `second_opinion` 里。注意：它和被测模型是同一家公司的，可能有一样的偏差。
7. **跑完系统之后，原则上不改标签。**只有两种情况可以改：案例输入写错了（打字错误、字段填错），或者你发现自己当初依据的事实是错的。**"系统的理由听起来更有道理"不算理由。**每次修改都要写进 `history`：改了什么、为什么改、是不是看了系统输出之后改的。评测报告里会公布修改次数。
8. **测试组的 10 个案例更严格。**除了改正事实错误，一律不改；也不能拿它们来调阈值。

## 五、常见陷阱

| 陷阱 | 表现 | 怎么避免 |
|---|---|---|
| 被名气带偏 | 大品牌就觉得可以接 | 第 3、4 步照样逐项检查 |
| 被个人喜好带偏 | 自己喜欢的品牌标得宽松 | 只按朋友的档案和价值观来判断，不按你自己的 |
| 照抄系统阈值 | "报价比 0.79，所以谈判" | 用"朋友接了会不会亏"来判断，不算比值 |
| 事后诸葛 | 看了系统结论再改答案 | 遵守第四节第 7 条 |
| 为了好看出题 | 只出系统容易答对的题 | 遵守第四节第 4 条，每类案例都要有难的 |
